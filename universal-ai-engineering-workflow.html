Universal AI Engineering Workflow

A team handbook for building software with OpenAI Codex and Anthropic Claude Code, written for the Hunger Learn repository and usable in any other repo.

Research cut-off: 25 November 2026. The tool facts come from the official Codex and Claude Code documentation as it read on that date, with Codex CLI 0.166.0 and Claude Code 2.1.332 installed locally. Both tools change monthly, so re-check anything marked Docs before you build on it.

1Executive summary

The question: if I were the Staff Engineer responsible for making this team excellent at AI-assisted development, what would I set up?

The short answer: make the repository, not the prompt, carry the quality bar. Both tools read the same contract and run the same checks. Every engineer follows the same risk-tiered lifecycle. A mistake that happens twice becomes a deterministic rule.

The ten decisions

  1. One shared contract: a short root AGENTS.md plus nested ones per package. Codex reads AGENTS.md natively. Claude Code reads it through a one-line CLAUDE.md that contains @AGENTS.md. Tool-specific files hold only tool-specific settings.
  2. One verification entrypoint, scripts/check. Agents, hooks, CI and humans all run the same command, so "done" means the same thing everywhere.
  3. Deterministic enforcement before prose. This follows Lauren Tan's trust pyramid. Architecture and APIs come first, then lint rules, types and tests, then runtime and formal verification. Written instructions come last.
  4. A correction ladder. Any review comment or agent mistake seen twice becomes a lint rule, type, test or architecture check. It becomes an instruction line only when it truly needs judgment.
  5. A risk-tiered lifecycle with four tiers: Minimal, Standard, Enhanced and High-risk. Each tier sets how much planning, review and verification a change gets.
  6. Test or reproduction first, then implementation. For bug fixes the agent must show a failing check before the fix, and the same check passing after it.
  7. Independent review in a fresh context, ideally from the other tool. Claude Code reviews Codex's diff and vice versa. AI review is advisory and never the approving reviewer.
  8. Evidence-carrying pull requests. Every PR carries the commands run, their output, and for UI changes screenshots or traces from a real run of the app. Reviewers review evidence as well as the diff.
  9. A small toolset. Use CLIs (gh, Playwright CLI, psql with a read-only role) and 6–9 shared Skills. No MCP server is mandatory. Each one must justify itself against an existing CLI.
  10. Humans own architecture, risk classification, merging and production. Agents never push to the default branch, bypass hooks, edit CI to get green, or auto-merge Enhanced or High-risk changes.

Why this shape

  • Talk Tan's central claim is that automating a sloppy inner loop just produces more slop. Her team invested in code-level constraints and verification before scaling throughput.
  • Docs Both vendors' guides say the same thing.
    • Claude Code's guide says to give the agent a way to verify its work, and that hooks are deterministic where CLAUDE.md is not.
    • Codex's guide says to define "done" up front, plan first for hard tasks, and turn repeated prompts into AGENTS.md or a skill.
  • Research Outside evidence is mixed.
    • DORA associates AI adoption with higher throughput and higher delivery instability.
    • METR's February 2026 update says AI speed-ups are now likely, but hard to measure.
    • Several 2026 studies find code review is becoming the bottleneck.
    Our takeaway: the gains are real but not automatic, and verification capacity is the constraint to invest in.
Caveat: nothing here guarantees the throughput or revert rates reported in the talk. Those are one team's self-reported numbers with no published baseline. Section 15 explains how we measure our own results.

3Lessons from Lauren Tan's talk

The talk is All Code Is Slop (Except Mine) by Lauren Tan ("poteto"), Grok Bot team, SpaceXSI. It was given at AI Engineer CODE 2026 in San Francisco on about 11 Nov 2026 and runs 17:31. Chapters: 0:00 slop to gold · 2:03 trust pyramid · 5:00 Dune · 6:56 comments → lint rules · 9:40 runtime verification & feature maps · 10:50 formal verification & UI testing · 11:51 spending tokens on verification · 13:32 11,000 PRs / 0.5% reverts · 15:11 foundations before software factories.

3.1 The trust pyramid (2:03)

Talk Tan calls it an inverse pyramid. It shows where to spend effort on an agent's environment. The widest layer, where most effort goes, sits at the top and lives in the code itself.

Talk Her reasoning: an agent's output is a function of its inputs, and the codebase is one of its largest inputs. Anti-patterns already in the code get copied, so "keep the garden clean". Her rule is that when you catch yourself correcting an agent, you should make that a deterministic check instead of adding another line to your rules or your agents.md. Code is far more reproducible, so you can trust it more.

Why this holds generally

  • An instruction is a probabilistic input. It competes with everything else in the context window, it can be summarised away during compaction, and it is applied unevenly.
  • A lint rule, type or test is evaluated on every change, by every tool and every engineer, in CI. It fails loudly with a specific message.
  • Claude Code's best-practices page makes the same distinction. It calls hooks the deterministic option, unlike CLAUDE.md. Docs
  • Prose is still the right tool for things that require judgment: product tone, Arabic copy quality, trade-offs.

3.2 Dune: architecture as a constraint (5:00)

Talk Dune is the Grok Bot team's client framework, "kind of like Next.js for Electron apps". Tan says it is not technically interesting. Its value is that it encodes lessons from building desktop apps as constraints. Her key line: anything that requires nuance to use well often leads to slop. Two examples:

  • useEffect is banned in product code. It is allowed only inside certain Dune APIs. She says this "categorically" removed a whole class of problems from code review.
  • The directory structure encodes the process boundary. There are top-level "Electron main" and "Electron renderer" directories. A dependency-graph analyzer and lint rules ban imports across the boundary. The speaker page adds that this stops main-process work that could freeze the UI.

Caveat The phrase "make the correct implementation the easiest implementation" does not appear verbatim in any source I could read. Her wording is "categorically eliminate that problem" through API design and architecture. The principle is the same, so I use it below as an interpretation.

How we apply it When a pattern needs nuance to use safely, wrap it in a narrow, well-named API, then ban the raw primitive outside that wrapper with a lint rule or import contract. Hunger Learn already does this in places, for example the read-only hl_readonly role behind readiness_v for text-to-SQL (see section 15).

3.3 Replacing comments and workarounds with rules (6:56)

Talk In Cursor, also an Electron app, agents patched mismatches between VS Code's imperative style and React's declarative style with setTimeout, requestAnimationFrame and requestIdleCallback.

  • These hacks caused garbage collection and jank.
  • The agents justified each hack in a code comment.
  • Other agents then read those comments as precedent and copied the hack.

The Grok Bot team responded in two ways.

  • They "decided to just ban 99% of comments", because comments go stale and spread workarounds.
  • They wrote lint rules whose error messages tell the agent to fix the root cause.

The specific rule names are not given.

The correction ladder When you see the same mistake twice, take the first rung that works:

1 · Make it impossibleChange the API or architecture so the wrong code can't be written (a wrapper, module boundary or DB role).
→
2 · Make it a typeBranded or opaque types, exhaustive unions, a zod schema at the boundary.
→
3 · Make it a lint ruleA built-in rule, no-restricted-imports, no-restricted-syntax, or a small custom rule whose message says what to do instead.
→
4 · Make it a testA regression, architecture (import contract) or property-based test that fails on the old code.
→
5 · Make it a CI gateWire the check into scripts/check and required status checks.
→
6 · Write it downOnly for judgment calls: one line in AGENTS.md or a Skill, saying why.

An adapted article on torchtree.com (19 Nov 2026) states the same discipline more concretely: the new check must fail on the old code and pass on the new. That is an interpretation of the talk, not something Tan said.

3.4 Runtime verification and Feature Maps (9:40)

Talk Tan made four points:

  • Agents run the real app themselves. She mentions the Chrome DevTools Protocol.
  • The team keeps a feature map: a user-facing "site map of all of the features", so "agents don't need to guess when you say … the thingy in the left sidebar".
  • Custom CLIs wrap the drivers, and skills reuse them. That "cuts down on token usage and is also testable".
  • Review is shifting to evidence: videos, screenshots, diagrams, formal verification.

Playwright is not named in the talk. Logs are not named explicitly either.

How we apply it

  • Feature map. Add docs/feature-map.md: one row per user-visible feature, giving its route, role, language, entry steps and the "proof" that it works. It doubles as the test plan for agents and humans.
  • One driver, not ad-hoc clicking. Write a small scripts/verify-app wrapper around the Playwright CLI or @playwright/test. It logs in as a seeded user, walks a named feature from the map, and saves screenshots, a trace, console errors and server logs to .verify/<branch>/.
  • Evidence in the PR. The PR template asks for the feature-map rows exercised and links to the artifacts.
  • Prefer CLIs to browser MCP servers when the agent has a shell. Playwright's own docs list the CLI as having lower token cost than MCP. Docs Independent benchmarks disagree on how big the gap is. Caveat

3.5 Formal verification and property-based testing (10:50)

Talk The team uses three techniques:

  • TLA+ model-checks major flows such as notifications across multiple devices and platforms.
  • Lean proves properties of their custom virtualization library, catching "flickering or jittering problems". She says it has found "quite a few bugs" but is "not a silver bullet".
  • Bombadil property-based UI testing has caught a few UI bugs.

A pstack statechart skill also draws user-facing state machines so humans can review them.

Use it when…

  • Property-based testing (Hypothesis, fast-check): pure functions with clear invariants, such as normalisers, parsers, hashing, matching, serialisation round-trips and idempotency. Agent-written property tests have found real bugs. Anthropic's Jan 2026 work found bugs in NumPy, SciPy and Pandas. Research
  • TLA+: concurrent or distributed protocols where interleavings matter, such as job queues, retries and multi-device sync, especially after a race bug has escaped.
  • Lean or other proof assistants: small, critical algorithms with precise specs, when you have someone who can review the spec.

Skip it when…

  • The feature is ordinary CRUD, UI layout, copy or glue code.
  • Nobody on the team can read or review the spec. An unreviewed model of the wrong system gives false confidence.
  • The behaviour is still changing weekly.
  • A good example-based test plus runtime verification already covers the risk.

3.6 Verification-heavy engineering (11:51)

Talk Tan says "most of my token usage goes to verification". She does not give a ratio for herself. She cites a colleague who couldn't trust agents six months earlier because subtle bugs were merging, and who now spends about 70% of her daily tokens on verification. She calls this a "golden age of software testing and verification", because agents make verification cheap to write.

In Codex and Claude Code terms

  • Write the acceptance criteria as executable checks first, and have the agent prove each one with a command and its output.
  • Use a separate session or subagent with fresh context to review and to try to break the change. Claude Code's guide recommends a reviewer that hasn't seen the code. Docs
  • Use native review commands: Codex /review, and Claude Code /code-review and /security-review. Docs
  • Run scripts/check from a hook so the agent cannot declare "done" with red checks. In Claude Code, a Stop hook that exits with code 2 sends the agent back to work. Docs
  • Budget verification explicitly in the issue: what must be shown, and how.

3.8 Foundations before software factories (15:11)

Talk "If your inner coding loop produces slop, then automating that loop just produces more slop." Her advice is to start with one lint rule, clean up old patterns, and make verification strong. Only then build "outer loop" automation, such as their routines that kick off cloud agents. This is exactly the order of our roadmap (section 16).

pstack is Tan's plugin in the Cursor plugins repo, MIT-licensed, with ports for Claude Code and Codex in community forks. It bundles skills such as /poteto-mode (a router), /how, /why, /architect, /interrogate, /tdd, /unslop, /no-comments and /correct, plus verification playbooks. It spends extra tokens on subagents and review panels. It is a useful reference for writing our own Skills. I don't recommend adopting it wholesale, because its defaults encode one person's workflow.

4Professional engineering practices

4.1 What serious teams converge on

The repo is the system of record

OpenAI, Feb 2026 In "Harness engineering", a team that builds with Codex reports three habits:

  • Architecture docs map domains and layering.
  • A quality document grades each domain over time.
  • Plans are first-class artifacts in the repo.

The engineer's job shifts toward designing environments, stating intent and building feedback loops.

Verification is the bottleneck to scale

Anthropic, 2026 Anthropic's Claude Code guidance centres on giving the agent a check to run and asking for evidence ("the command it ran and its output, or the screenshot").

Caveat Secondary coverage of a Nov 2026 Anthropic post says verification loops are what allow many agents to run in parallel. I could not read the primary post, so treat this as unconfirmed.

Define "done" before starting

Codex best practices

  • Define done up front: tests pass, behaviour changed, bug no longer reproduces.
  • Use Plan mode for hard tasks.
  • Review the diff.
  • Move repeated prompts into AGENTS.md or a skill.
  • Start with tight permissions.

Review capacity, not generation, limits throughput

Research, 2026

  • A study of 1.02 million PRs across 207 projects frames review and integration as the downstream bottleneck as AI raises change volume.
  • Another found that, once adopted, suggestions from AI review agents increased code complexity and size more than human suggestions did.
  • Vendor data says AI-authored PRs carry more issues. CodeRabbit (Dec 2025) found about 1.7× more. Vendor

4.2 What the outcome evidence says

  • DORA Higher AI adoption is associated with higher throughput and higher delivery instability. The 2026 ROI report argues that strong foundations decide whether AI pays off, and expects a temporary dip before gains (a "J-curve"). Some of its headline numbers are model inputs, not measurements. Caveat
  • METR
    • The Jul 2025 randomised trial found experienced open-source developers were 19% slower with early-2025 tools, while believing they were faster.
    • The Feb 2026 update says developers are now likely sped up, but selection effects make clean measurement hard. Its own estimate is called a likely lower bound.
  • Implication Measure our own baseline before and after rollout (section 15.10). Perception is not evidence, and METR's original finding showed the gap can be large.

6Universal team workflow

6.1 Critique of the proposed 12-step workflow

The proposed flow was: issue → explore → plan → review plan → implement → tests → local verification → independent review → CI → human review → merge → learn. It has the right shape. It has eight gaps:

  1. No risk classification. A typo fix and an auth change get the same process, which makes the process both too heavy and too light.
  2. Tests come after implementation. That invites tests fitted to the code. A bug fix should start with a failing reproduction, and a feature should start with acceptance checks.
  3. "Review the plan when necessary" is undefined. The tier decides when.
  4. No verification plan in the issue. "How will we know it works?" must be answered before coding, including which feature-map rows to exercise.
  5. No protection against weakened checks. Agents can delete or skip tests, loosen types, add eslint-disable, or edit CI. These need deterministic guards.
  6. Humans review the whole diff without evidence. That is the bottleneck the research warns about. Reviewers should see evidence, and attention should go to risky paths.
  7. "Learn" is vague. It needs a concrete mechanism: the correction ladder, with an owner.
  8. Deployment safety is missing: rollback, feature flags, post-deploy checks.

6.2 The improved lifecycle

6.3 Four workflow tiers

The engineer picks the tier at triage. If in doubt, go up one tier. Some paths force a minimum tier, and CODEOWNERS enforces it (section 15).

6.4 One agent, two agents, or many?

  • One agent: the default. Minimal and Standard tasks, and any task where the spec is still forming.
  • Two agents (writer + reviewer): Enhanced and High-risk tasks, or any time you would want a second pair of eyes. The reviewer must start from a fresh context with only the diff, the issue and the evidence. Use the other tool when you can, because its blind spots are different.
  • Several parallel agents: only when the work splits into pieces with disjoint file ownership and a clear interface, such as independent docproc and web tasks, a test backfill per module, or docs. See section 13 for when parallelism stops paying.

The round limit follows the same reasoning as Claude Code's built-in Stop-hook block cap (8 consecutive blocks by default). Loops that don't converge mean the spec or the design is wrong, and a human should step in.

8Skills strategy

Docs Both tools follow the open Agent Skills format: a folder with a SKILL.md (YAML frontmatter plus Markdown), and optional scripts/, references/ and assets/. Loading is progressive: only the name and description sit in context until the skill is used. The spec advises keeping SKILL.md under about 500 lines and 5,000 tokens.

8.1 Portable skill rules

  • Use only the name and description frontmatter in shared Skills. Those are the fields both tools document. Put Codex extras in agents/openai.yaml. Add Claude-only frontmatter only where it's needed, and confirm Codex still loads the skill.
  • Write the description as when to use it and when not to. Both tools use it to decide implicit invocation.
  • Put deterministic steps in scripts/ and have the Skill call them. A script is testable, cheaper, and identical in both tools.
  • Refer to commands, not tool names. Write "run scripts/check", not "use the Bash tool".
  • Skills are code: reviewed in PRs, owned, versioned, and evaluated (section 11.4).

11.3 Guarding the guards

Agents optimise for green checks, so protect the checks themselves:

  • scripts/guard-diff in CI fails when the diff does any of the following, unless a human adds the allow-weakening label with a reason:
    • adds .skip, .only, @pytest.mark.skip or xfail;
    • adds eslint-disable, @ts-ignore or @ts-expect-error;
    • adds type: ignore or # noqa;
    • deletes test files;
    • lowers coverage thresholds.
  • CODEOWNERS on .github/, scripts/, hook configs and lint configs, so agents can't quietly relax the rules.
  • Sandbox protection. Codex's workspace-write mode already protects .git and .codex. Docs In Claude Code, add deny rules for editing hook and CI files during agent sessions.

11.4 Evaluating AI features and our own Skills

  • Product AI (Hunger Learn): the repo already has the right bones.
    • A 15-document synthetic SOP corpus with gold labels, split into dev/ and held_out/.
    • Quote validation.
    • An LLM judge for generated training.
    Turn these into a repeatable eval command with stored baselines. Any prompt or model change must show its delta on dev. Only frozen configurations run on held_out.
  • Skills and agent workflows: evaluate the shared Skills the way a product feature is evaluated.
    • Write a few graded cases per Skill.

    • Run 3–5 trials per arm. Effects of a few points are noise at that size.
  • Anthropic, Jan 2026 Evals for agents should start narrow and grow with real failure cases. Combine them with production monitoring. Infrastructure noise alone can move agentic coding benchmarks by several points.

12CI/CD architecture

Mandatory

  • Branch protection on main: PR required, no force-push, no direct pushes, required status checks, and at least one human approval.
  • Required checks: lint and format, typecheck, unit tests, integration tests, build, guard-diff, secret scan.
  • Code-owner review on High-risk paths.
  • Agents work only on branches or worktrees and open PRs. Hooks are never bypassed (--no-verify is denied in the agents' permission rules).
  • Rollback path known before merging Enhanced and High-risk changes.

Optional, adopt when useful

  • An AI review bot (@codex review, claude-code-action, or managed Code Review). Its comments are advisory, and it never approves.
  • SAST (CodeQL or Semgrep). CodeQL on private repos needs GitHub Advanced Security.
  • Dependency audit as blocking (start as a warning).
  • Preview deployments with verify-app against them.
  • Auto-merge only for Minimal-tier dependency patch bumps with green checks, never for Enhanced or High-risk.

13Parallel agent workflows

Parallelism helps when…

  • Tasks have disjoint file ownership, e.g. a docproc fix and a web copy change.
  • There is a fixed interface between parts (a schema, an API contract, a types file) written and merged first.
  • The work is "embarrassingly parallel": test backfill per module, lint-rule migrations per directory, docs, or investigating several hypotheses read-only.
  • Verification is automated enough that you can trust results without watching each agent.

…and hurts when

  • Two agents touch the same files, the same migration sequence, or shared config such as i18n dictionaries or lockfiles.
  • The spec is still being discovered. Parallel agents multiply the wrong guess.
  • Human review capacity is already the bottleneck. More PRs make it worse (section 4.1).
  • Every agent reloads the same large context, which costs tokens and time. Claude Code's guidance recommends restraint.

Collaboration model across engineers and tools

  1. The issue is the unit of ownership. One issue gets one branch and one owner (an engineer). Any number of agents can help, but the engineer is accountable.
  2. Each parallel agent works in its own worktree and branch (claude --worktree <name>, subagent isolation: worktree, or Codex app worktrees). Gitignored files the app needs, such as .env.local, are listed in .worktreeinclude for Claude Code.
  3. Claim files in the plan. The plan lists the paths each sub-task will touch. Overlapping claims mean the tasks must be serialised.
  4. Interface first. Shared types and contracts land in their own small PR before dependent work starts.
  5. Shared context lives in the repo, in AGENTS.md, plans and the feature map, not in someone's chat. Any engineer, using either tool, can pick up any branch.
  6. Separate implementation and review. The reviewer is a different session, preferably the other tool, preferably not the engineer who prompted the writer.
  7. Avoid duplicate work. Assign issues on GitHub before starting, and link draft PRs early.

Local resources need extra care here. The Postgres container is shared (127.0.0.1:5442), and the GPU render queue is serialised. Parallel agents running migrations or renders will collide. Give each worktree its own database name, or serialise DB-touching tasks.

15.5 Avoid

  • Building a custom orchestrator or harness. Both tools already ship subagents, worktrees, hooks, review and headless modes.
  • Growing AGENTS.md past about 150 lines, or duplicating rules across CLAUDE.md, AGENTS.md and Skills.
  • Installing MCP servers "just in case", especially ones with write access to cloud resources.
  • Auto-merging agent PRs beyond Minimal-tier dependency bumps.
  • Making an AI reviewer a required approver, or treating "the agent said tests pass" as evidence without the output.
  • Running parallel agents against the shared Postgres or GPU queue without isolation.
  • Using formal methods on CRUD and UI, or vendor productivity numbers as targets.
  • Using held-out SOP data during prompt development. The repo's rule is correct, so enforce it by keeping held_out/ out of agent-readable paths during dev work.

15.6 Human-controlled, always

  • Risk tier and acceptance criteria.
  • Architecture decisions (ADRs), new dependencies, and changes to DB roles and grants.
  • Merging to main, deploying, rollback calls, incident triage.
  • Publishing training content to learners. The product already requires human approval here; keep it.
  • Changes to CI, hooks, lint configs and CODEOWNERS.
  • Anything touching held_out/ evaluation.

16Adoption roadmap

There are no calendar deadlines. Each phase ends when its completion criteria are met. For a small team, Phase 1 is a few days of work. Later phases depend on how fast the checks become trusted.

Phase 1: Foundation
  • Goals: one source of instructions, one verification command, checks that always run.
  • Tools: GitHub Actions, gh, ruff (format and lint, start lenient), existing ESLint and tsc, pytest.
  • Steps:
    1. Commit the baseline.
    2. Write AGENTS.md (root and nested), and make CLAUDE.md → @AGENTS.md.
    3. Add scripts/check and scripts/check-fast.
    4. Add ci.yml (section 12).
    5. Add branch protection with required checks.
    6. Add the .claude/skills link.
    7. Install bubblewrap + socat and enable sandboxes.
  • Benefits: both tools see the same rules, "done" is objective, and regressions get caught.
  • Risks: a slow or flaky CI erodes trust. Keep it under about 10 minutes and quarantine flaky tests.
  • Done when: every PR runs the required checks. Both tools load the same instructions (verify with /memory or /context in Claude Code and the Codex session log). scripts/check passes on main.
Phase 2: Standard workflow
  • Goals: every change follows the tiered lifecycle.
  • Tools: issue and PR templates, CODEOWNERS, plan mode in both tools, native review commands.
  • Steps:
    1. Publish the tiers and High-risk path list.
    2. Make test-first the default for bugs.
    3. Run cross-tool fresh-context review on Enhanced and High-risk changes.
    4. Backfill web tests for auth, sessions and server actions.
    5. Ratchet in ruff, pyright and stricter ESLint per directory.
    6. Start the metrics baseline.
  • Benefits: predictable quality, and faster review because evidence arrives with the PR.
  • Risks: process feeling heavy. Keep the Minimal tier genuinely light.
  • Done when: most PRs carry a tier and evidence, and High-risk PRs have code-owner approval.
Phase 3: Automation
  • Goals: procedures become Skills, and mistakes become rules.
  • Tools: shared Skills, hooks in both tools, guard-diff, gitleaks, import-linter, Hypothesis, and optionally an AI review bot.
  • Steps:
    1. Write the six Skills and the reviewer subagents.
    2. Add Stop hooks → check-fast.
    3. Add guard-diff and gitleaks as required checks.
    4. Encode the invariants from section 15.2.
    5. Add a small graded eval per Skill.
    6. Disable unused MCP servers and plugins.
  • Benefits: less re-prompting, and fewer repeat review comments.
  • Risks: Skills that drift from reality. Give each Skill an owner and an eval case.
  • Done when: a mistake seen twice becomes a rule within a week, and both tools list and use the same Skills.
Phase 4: Advanced engineering
  • Goals: runtime evidence, AI-feature evals, and safe parallelism.
  • Tools: Playwright, docs/feature-map.md, scripts/verify-app, the eval command, worktrees, per-worktree databases, and optionally TLA+.
  • Steps:
    1. Build verify-app over the F01–F07 rows in both languages.
    2. Add evidence upload to PRs.
    3. Build the eval command over the synthetic corpus and generator.
    4. Run parallel worktree tasks with file claims.
    5. Add architecture contracts.
    6. Consider formal models only for proven concurrency risk.
  • Benefits: agents can prove UI and AI behaviour, and humans review outcomes.
  • Risks: brittle end-to-end tests. Test user-visible contracts, not DOM details.
  • Done when: UI PRs ship runtime evidence, prompt and model changes ship eval deltas, and parallel work causes no merge collisions.

Rolling it out to the team:

  1. One owner, the Staff Engineer, writes Phase 1 in a single PR that everyone reviews.
  2. Pair-run the workflow on two real issues, one with each tool.
  3. Hold a short demo of the correction ladder using a real repeated mistake.
  4. Run a fortnightly 30-minute retro: which comments repeated, which rules were added, which Skills misfired.
  5. Change the standard only through PRs to AGENTS.md and Skills.

17Team standards and checklists

Before starting a task

  • Issue has acceptance criteria and a verification plan
  • Risk tier chosen (go higher if unsure)
  • Branch or worktree created; issue assigned to me
  • For parallel work: file claims don't overlap

Agent session done means

  • Failing test shown before the fix (bugs and features)
  • scripts/check passed (output pasted)
  • UI: verify-app evidence for touched rows, AR and EN
  • No skipped or deleted tests, suppressions or CI edits
  • Diff limited to the issue's scope

PR author

  • Tier, issue link, summary of behaviour change
  • Evidence: commands + output, screenshots, eval deltas
  • Risks and rollback plan (Enhanced and High-risk)
  • Fresh-context review done; must-fix items resolved
  • Small enough to review in one sitting

Human reviewer

  • Evidence matches every acceptance criterion
  • Tests would fail without the change
  • High-risk paths read line by line
  • No new dependency, permission or role without an ADR
  • Anything I'd comment on twice → encode-mistake

After an incident or repeated mistake

  • Root cause written in two sentences
  • Highest workable ladder rung chosen and implemented
  • New check proven to fail on the bad pattern
  • Logged in docs/rules-log.md

New repository onboarding

  • AGENTS.md + CLAUDE.md bridge
  • scripts/check + CI + branch protection
  • .agents/skills (+ .claude/skills link)
  • Hooks in both tools calling check-fast
  • Templates + CODEOWNERS + feature map if there's a UI
