Decisions already made

  • Keep docproc as a Python service (LangGraph, OvisOCR3 for scans, BGE-M3 embeddings). Don't rewrite it.
  • Thin end-to-end: all 6 stages work, each kept minimal.
  • LLM = OpenRouter or local Ollama, switched by env vars. Both speak the OpenAI API, so one adapter serves both.
  • Evals before features: the 15-doc golden set is the scoreboard.

Stage 2AI SDKZod

Training per role, generated once, and provably grounded in its clause.

  • generateObject with a Zod schema: lesson, scenario, 5–10 questions per procedure

Human approval

Stage 3Auth roles

Nothing reaches a learner until a trainer says yes.

  • Review queue: item beside its source clause, ⚠ items first
  • Approve · edit · reject (reject regenerates the item)
  • Lifecycle: draft → verified → approved → published → outdated
  • Audit log: who, what, when, which clause version
Done when: a rejected item comes back regenerated, and learners only ever query published items (enforced by RLS).

v2 loop + demo

Stage 6COST

The money shot: a new version only redoes what changed.

  • Upload v2 → docproc diff

Demo script: the "awesome work!!!" moments

Six minutes, one story, real data from the corpus.

  1. It reads anything. Upload an Arabic scan. Clauses appear with page citations, beside the source text.
  2. It refuses to make things up. A generated item whose quote isn't in the clause is flagged ⚠ and blocked before review.
  3. A human is always in charge. The trainer approves, edits or rejects, and every action lands in the audit log.
  4. One SOP, three learners. A courier on a phone, an employee on a laptop and a partner on a tablet each get their own format.
  5. Ask in Arabic. «من لم يتقن…؟» returns a list of names from read-only views.
  6. v2 costs almost nothing. Upload the new version: 10 of 11 clauses are kept at $0, and only the 15→10-minute rule goes back for approval. Then show the eval scoreboard on the held-out set.

Engineering rules we follow

From the engineering-best-practices skill, applied to this project.

Workflows, not agents

Every stage is a fixed pipeline. The steps are known in advance, so no autonomous agent is needed.

Schemas at every AI edge

Pydantic in Python, Zod in TypeScript. Invalid output is retried with the error fed back.

Evals before features

The golden set exists. Score every change against it, and keep held-out untouched.

Fail loudly

A 0-clause run is incomplete, not a success. Errors carry the file, page and request context.

Least privilege

RLS per role. Text-to-SQL sees read-only views only, and publishing needs a human.

Every AI call is logged

Model, prompt version, tokens, cost and latency, so the cost-per-doc metric is real.

How we verify each phase

Automated

  • pytest -q stays green, including Postgres parity
  • Eval metrics after each phase, compared with the previous run
  • Type checks and lint in both Python and TypeScript

By hand

  • Phone-width check of the learner screens, in RTL
  • One held-out run with frozen config before the demo
